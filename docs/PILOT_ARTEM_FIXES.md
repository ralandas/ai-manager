Разбор жалоб: `docs/PILOT_ARTEM_FEEDBACK.md`.

Легенда приоритета:

- **P0** — врать гостю / терять бронь
- **P1** — диалог разваливается
- **P2** — UX, не блокер продажи

## P0. Не врать цифры и ссылки

### P0-1. Заезд / выезд брать из гостиницы Bnovo, не из промпта Читы

**Сейчас:** промпт и дефолты коннектора — 14:00 / 12:00, поздний выезд 350 ₽/час.  
**Надо:** читать настройки гостиницы (скрин: заезд **15:00**, выезд **11:00**) и отдавать агенту инструментом (`get_house_rules` / поля в `check_availability`). Из промпта **вырезать** 14:00, 12:00, 350 ₽.

Файлы: `src/pms/bnovo.ts`, `src/pms/types.ts`, `src/agent/prompt.ts`, `src/agent/tools.ts`.

### P0-2. Ранний заезд / поздний выезд — из тарифа

**Сейчас:** модель фантазирует «350 ₽/час / бронь предыдущих суток».  
**Надо:** парсить блок тарифа «Ранний заезд и поздний выезд» (у пилота: **50% текущих суток**). Считать сумму от цены ночи выбранного тарифа. Не называть цену, пока инструмент не вернул число.

### P0-3. Запретить выдуманные URL

**Сейчас:** `https://bnovo.ru/apartment/{id}` — 404. `get_apartment_info` в direct-PMS падает.  
**Надо:**

1. В Bnovo-режиме `get_apartment_info` не ходить в нашу БД.
2. Либо отдать **рабочий** URL (если есть reservationsteps / свой `/apt/:id` с данными из презентации), либо честно: «отдельной страницы нет, вот адрес и метро, фото сейчас пришлю».
3. В промпте запретить домены `bnovo.ru/apartment`, `example.com` и любой URL не из инструмента.

Карту «я уже скинула» без факта отправки — запретить.

### P0-4. Несколько тарифов, не один `planId`

**Сейчас:** один `planId` (`53582` / из creds). Мин. срок 5 ночей → «занято», хотя другой тариф продаёт 3 ночи дороже.

**Надо:**

1. Список тарифов, у которых включён **«Модуль бронирования»** (как на скрине клиента).
2. `check_availability`: по комнате перебрать эти тарифы, взять **самый дешёвый, которым период реально продаётся**.
3. В результате отдать `planId` + minStay **этого** тарифа, чтобы `create_booking` писал тот же план.
4. Если дешёвый тариф требует 5 ночей, а есть дороже на 3 — показывать оба или явно: «на 3 ночи есть, дороже».

Пока это не сделано — бот будет врать «нельзя», когда продавать можно.

### P0-5. Список и бронь должны говорить одно и то же

**Сейчас:** 5-я Красноармейская в выдаче на 3 ночи → после согласия «минимум 5» → после «ок, 5 ночей» «уже недоступна».

**Надо:**

- Не показывать комнату в `results`, если её нельзя забронировать на **эти** даты (minStay / closedArrival / нет цены ни на одном модульном тарифе / занята в календаре).
- Перед `create_booking` повторно проверить тот же тариф+даты; если блок — объяснить **причину** (заняты доп. ночи / minStay / тариф), не общее «занята».
- Не предлагать «продлите до 5 ночей», не проверив, что 5 ночей на этой комнате свободны.

### P0-6. Не продавать прошедшие даты

Отсекать `checkIn < сегодня` в `check_availability` (и в create). Сообщение: «эти даты уже прошли, назовите актуальные». Не гонять воронку до имени/телефона.

### P0-7. Не выдумывать оснащение (парковка и т.п.)

Если в описании Bnovo нет парковки — «в карточке не указано, уточню у администратора», не «бесплатная у дома».  
Парковку «день платно / ночь бесплатно» клиент сказал **в Bnovo нет** — это ручной факт хозяина; либо поле в кабинете агента, либо не трогать.

## P1. Диалог перестаёт быть диалогом

### P1-1. Не переспрашивать то, что гость уже сказал

Если есть даты + гости + «центр/все» — следующий шаг: список или «все не влезут, вот N, остальные по запросу». Запретить второй раз спрашивать район/метро в том же ходе.

### P1-2. «Покажи все» значит все (в разумном виде)

- Текстом: если гость сказал «все / скиньте все» — перечислить **весь** `results` (пачками по 8–10 с «ещё N»), не «4 самых интересных».
- Фото: поднять или убрать `MAX_APTS = 4`, либо слать пачками по remaining, пока гость не остановит. Не обещать «все», отправив 4.

### P1-3. Прозрачный выбор, не «самые интересные»

В каждом списке: сортировка (дешевле → дороже) и строка «показано K из total». Логика «почему эти» должна быть читаемой.

### P1-4. Один вопрос — одно сообщение

Постобработка reply: если два абзаца почти одинаковые — оставить один. Loop-guard смотреть и **внутри** текущего ответа.

### P1-5. Не слать одно и то же фото дважды

Память чата: `sentPhotoKeys = title|price` (или propertyId). Повторный `send_apartment_photos` по тому же id в том же диалоге — skip.

### P1-6. Скорость ответа

Цель: **< 15 с** на текстовый ход без фото.

Идеи (не все сразу):

- не блокировать poll всего бота одним ходом (очередь чатов);
- кэш `check_availability` на (даты, guests, plan) на 1–2 мин;
- не звать повторный check с теми же аргументами в одном диалоге;
- фото — только после явного «скинь фото», не в том же ходе, что большой поиск;
- не ретраить LLM 3×30 с на каждом hop, если Bnovo уже ответил.

4 минуты на «где квартира?» — неприемлемо.

### P1-7. История брони не должна всплывать не в тему

Скрин: «Пришлите информацию по заезду 24–27 августа» → «Эта бронь была снята из-за неоплаты». Промпт это уже запрещает — усилить: на новый запрос дат **не** поднимать старый `lastBookingId`, пока гость сам не спросил про оплату.

## P2. Продукт «нажал — увидел квартиру»

### P2-1. Карточка варианта

Клиент: картинки и описание при нажатии на предложение.

Варианты:

- наша страница `/apt/:bnovoId` из презентации Bnovo (фото, описание, метро, адрес) + ссылка в чате;
- или Telegram: одно фото-превью + кнопка «ещё фото / описание» (если остаёмся в user-аккаунте, inline-кнопок как у бота может не быть — тогда только URL).

Пока нет рабочей ссылки — P0-3 обязателен.

### P2-2. Человеческие названия комнат

Не показывать служебные коды (`мож2`). Только адрес из презентации / `name`. Код — во внутренний id.

### P2-3. Промпт очистить от Читы

Вычистить OneDayDom: техбалкон, 350 ₽, 14:00/12:00, «Багдарин», залог 2500 как поведение по умолчанию. Питерский пилот живёт правилами Bnovo этого аккаунта.

## Порядок внедрения (чтобы закрыть пилот)

1. **P0-6 + P0-3 + P0-7** — быстро, без нового парсинга кабинета: валидация дат, запрет фейк-URL, «нет в описании = не выдумывать».
2. **P0-1 + P0-2** — один запрос настроек гостиницы + правила тарифа.
3. **P0-4 + P0-5** — обход тарифов с «Модуль бронирования» + согласованность list/book. Это главный «занято, хотя можно продать».
4. **P1-1…P1-5** — диалог (все / без дублей / без двойных вопросов).
5. **P1-6** — скорость.
6. **P2-1** — страница квартиры как ответ на «ссылки кривые» и хотелку «по нажатию».

## Что не чинить в коде (явно)

| Тема | Почему |
|------|--------|
| Парковка день/ночь в Bnovo | Клиент: «это уже никак» — поля нет. Только ручной текст в описании/кабинете агента. |
| Живая карта внутри чата без URL | Нужен свой `/apt` или внешний reservationsteps. Сам Telegram карту не встроит в user-аккаунт. |

## Критерий «пилот снова можно отдавать»

- Нет ссылок, которые не открываются.
- Заезд/выезд в чате = 15:00 / 11:00 (или что стоит в гостинице).
- Ранний заезд считается как в тарифе (50% суток), не 350 ₽.
- На 3 ночи, если есть тариф на 3 ночи — квартира **в списке и бронируется**, даже если другой тариф хочет 5.
- «Скиньте все» даёт полный список, не 4 штуки.
- Прошедшие даты отсекаются сразу.
- Повтор того же альбома / того же вопроса в одном ходе — нет.
- Ответ без фото обычно < 15 с.
