# AI Manager — администратор посуточной аренды

ИИ-агент, который ведёт переписку с клиентом в мессенджере, продаёт, сам создаёт
бронирование в PMS (Realty Calendar), выдаёт ссылку на оплату, а также раздаёт
задачи горничным (прогноз выездов на завтра).

**Пилот:** мессенджер — Telegram, LLM — Gemini, PMS — Realty Calendar.
Max (через Wapi) подключается позже за тем же интерфейсом мессенджера.

## Архитектура (слои за абстракциями)

- `src/messenger/` — интерфейс `Messenger` + Telegram-коннектор (позже Max/Wapi).
- `src/llm/` — интерфейс `LlmProvider` + Gemini (позже можно Claude/OpenAI).
- `src/pms/` — интерфейс `PmsConnector` + `stub` (позже `realtycalendar`).
- `src/agent/` — системный промпт, инструменты (tools), диалоговый движок.
- `src/safety.ts` — предохранители: kill-switch, валидация, идемпотентность, аудит.
- `src/housekeeping.ts` — прогноз выездов + вечерний планировщик.

Ничто в агенте не знает про конкретный мессенджер/PMS/LLM — только про интерфейсы.
Поэтому переключение Telegram→Max или stub→Realty Calendar меняет один файл.

## Запуск (локально)

```bash
npm install
cp .env.example .env      # заполнить GEMINI_API_KEY и TELEGRAM_BOT_TOKEN
npm run dev
```

Для локального приёма вебхуков Telegram нужен публичный HTTPS — туннель
(cloudflared/ngrok) и `PUBLIC_URL=<туннель>` в `.env`. На VPS — реальный домен.

Проверка: `GET /health`. Ручной прогон прогноза горничным: `POST /admin/forecast`.

## Предохранители (агент автономен на деньгах)

- `AUTONOMY_ENABLED=false` — мгновенно замораживает создание броней и выдачу оплаты.
- `MIN_BOOKING_TOTAL` / `MAX_BOOKING_TOTAL` — отсекают подозрительные суммы.
- Идемпотентность броней — повтор/сбой не создаёт дубль.
- Каждое денежное действие пишется в аудит-лог и уведомляет `OWNER_CHAT_ID`.

## PMS Realty Calendar — что нужно выяснить (реверс веб-клиента)

У Realty Calendar нет официального API. Реальный коннектор пишется по сетевым
запросам из веб-кабинета. Когда будет доступ — в DevTools → Network пройти
сценарии и заполнить `pms-contract.md`:

1. **Авторизация**: как передаётся (кука/токен/заголовок), срок жизни, есть ли refresh.
2. **Список объектов**: эндпоинт, формат ответа.
3. **Проверка доступности / цена** на диапазон дат.
4. **Создание брони**: один запрос или цепочка; какие поля обязательны.
5. **Ссылка на оплату**: отдельный эндпоинт или часть UI; как связана с бронью.
6. **Выезды на дату**: эндпоинт списка выездов/заездов (для прогноза горничным).
7. Rate limits / антибот, стабильность.

Пока не заполнено — работает `PMS_PROVIDER=stub` (данные в памяти), на нём
отлаживается весь диалог, продажа и модуль горничных.
